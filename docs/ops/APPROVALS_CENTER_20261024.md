## AI-proposed conflict rules (batch 35, 2026-10-25)

Source `conflict_rule_proposals` reads `scripts/lib/conflicts/proposals.collection(status=PENDING)` (the same store as
`GET /api/v3/conflicts/proposals`, docs/ops/CONFLICT_RULE_PROPOSALS.md §4–5). Each pending `RuleProposal` becomes one
`CONFLICT` item `rule-proposal:<proposal_id>` with `decision_mode=GOVERNED_PATH` and
`governed_href=/conflicts/rules?proposal=<id>`; approved/rejected proposals never appear. The queue row links straight
to that proposal's sheet (← Back returns to the queue). The ledger refuses APPROVE for it (`GOVERNED_ACTION_REQUIRED`)
and a recorded disposition never hides it: Approve / Edit then approve / Reject happen only on the Conflict rules page,
with its own operator identity, CSRF and activation gate. An unreadable or truncated store is a named gap
(`pending_count` null), never zero. The pending items count in `pending_count` and `queue_summary.by_type.conflict`.
The header/Home ⚑ approvals count stays the financial queue total (W1 `approvals.total`), which this queue must not
replace.

`operator_approvals_api.handle(path, method, body, query)` owns
`/api/v2/governance/approvals`, `/approvals/:id`, `/approvals/:id/open`,
`/approvals/:id/read`, `/approvals/:id/decide`, `/policy`, `/policy/feedback`.
The prefix is `/api/v2/governance` in every route above. Queue responses omit
document bodies and page 50 cards. Reader responses contain one bounded document;
Rulebook responses page 40 blocks by section.

`queue_summary` reports `scope=all_operator_approvals`, typed known administrative and financial
counts, `pending_count`, `known_pending_count`, `complete`, `gaps`, `as_of`.
It must not replace the financial approval count. The W1 `financial_queue_items` adapter supplies bounded rows and explicit causal references. Missing W1 or W10 integration keeps the all-queue total null with a named source gap. Only explicit authoritative references remove overlap; titles, symbols and account labels never do. The queue does not silently add counts
from different projections. Old decisions remove only the matching item ID AND
document hash, so amended text reappears.

Hash chaining detects modification but is not a cryptographic signature. The
decision's actor is the authenticated request principal, never a body field.
Read markers attest the authenticated browser's viewport observations; a server
cannot independently prove what a human perceived.

## Author explanations

The existing PR body may include a fenced `approval-reader-notes` JSON block
with `head_sha` equal to the full PR head and `annotations` mapping stable reader
change IDs to `{plain, reason}`. Only current change IDs and bounded strings
are accepted. Old-head or malformed notes are ignored. The document fingerprint
includes these notes, so edited explanations reset the review too. Missing notes
remain an explicit gap; no model invents the author’s reason during a GET.

## Release layout

Served artifacts have no `.git`. The reader uses that artifact’s own full source
stamps through `runtime_identity` with environment/current-link fallbacks
disabled. Immutable blob reads use the existing canonical repository explicitly;
Git never searches a release’s parents. Policy history is anchored to the
artifact commit, so a canonical checkout that has moved ahead cannot change the
policy being read. Disagreeing stamps or deployed wording are refused without
repair. A read-only check against the actual CURRENT release matched its 624,051
policy characters and exact source identity; isolated real-Git tests also cover
ahead checkouts, malicious environment overrides and artifact mismatch.
