## A. Steer the tmux Claude sessions from the phone: Claude Code Remote Control

### A.1 Requirements (docs)

- Plan: Pro, Max, Team or Enterprise. **API keys are not supported.** On Team/Enterprise an Owner must turn
  on the Remote Control toggle in Claude Code admin settings.
- Login: the session must be signed in through claude.ai (`/login`). Check with `/status` in the session.
- Not available if `ANTHROPIC_BASE_URL` points anywhere but `api.anthropic.com`, or under Bedrock/Vertex/Foundry,
  or if `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` or `DISABLE_GROWTHBOOK` is set.
- Phone: the Claude app (iOS/Android), signed in to **the same account and organization** as the terminal.
  `/mobile` in Claude Code shows a QR code for the app store page.
- Version: the docs name several minimums (v2.1.200 resume flags, v2.1.224 dialog expiry, v2.1.238 model
  pick from device, v2.1.283 telemetry-variable case). ms01 has 2.1.288, which is above all of them.
- Remote Control is off for orgs with Zero Data Retention or the HIPAA configuration.

### A.2 Start it in a session that is already running (the tmux case)

The existing sessions (`tmux ls` on 2026-10-09: `claude`, `claude1`, `codex`, `agent1_codex`, `agent2_grok`,
`grokb`) keep running; Remote Control attaches to one of them and carries over its history.

1. From a terminal on ms01 (or over SSH via Tailscale): `tmux attach -t claude`
2. At the Claude Code prompt type: `/remote-control ms01 claude` (alias `/rc`; the argument is the session
   title shown on the phone; name each session distinctly, e.g. `ms01 claude1`).
3. The first time, a dialog asks to confirm; choose **Enable Remote Control**.
4. The prompt line shows `/rc active`. Running `/remote-control` again opens the status panel with the
   session URL and a QR code.
5. Detach tmux (`Ctrl-b d`). The `claude` process must keep running; tmux is what keeps it alive.
6. On the phone: Claude app, tap **Code**, then pick the session (computer icon, green dot = online), or
   scan the QR code.

Docs constraint: outside server mode, **one remote session per interactive process**. Each tmux session is
its own process, so each can carry its own Remote Control session.

Alternatives in the docs, not needed for the tmux case: `claude --remote-control "name"` (new interactive
session with RC on) and `claude remote-control` (server mode, multiple sessions, `--spawn worktree`).
Auto-connect for all sessions (`/config` -> Enable Remote Control for all sessions, or
`remoteControlAtStartup`) is **not recommended** here: it would expose every agent session, not just the ones
the operator chose.

### A.3 Approvals and push notifications

- Permission prompts and `AskUserQuestion` questions are forwarded to the connected device and stay open until
  answered, either on the phone or in the terminal. Other forwarded dialogs expire after 5 minutes by default
  (`dialogExpiry`).
- Push: install the app, sign in, allow notifications, then in the terminal session run `/config` and turn on
  **Push when actions required** (permission prompts and questions) and, if wanted, **Push when Claude
  decides** (task finished / needs a decision). If `/config` shows **No mobile registered**, open the app once.
  iOS Focus modes and notification summaries can delay pushes (Settings -> Notifications -> Claude).
- Pushes are skipped while you are typing in, or focused on, the connected terminal.
- **What a tap approves:** one Claude Code tool call in that session. It does **not** create, consume or
  replace a guard grant. Any action that needs a guard tier (config-write, release, push budget, etc.)
  still needs a grant in the guard ledger through the existing Telegram approval code flow. A Remote Control
  approval must never be used to retry a guard denial (AGENTS.md: never route around a denial).

### A.4 End it

- In the tmux session run `/remote-control` and use the status panel to disconnect. (The docs say the panel
  "also lets you dis[connect]"; the VS Code and Desktop instructions say "To disconnect, run `/remote-control`
  again". The exact CLI wording is **NOT VERIFIED**.)
- Or end/archive the session from the phone. The terminal then reports "This session was ended or archived
  from another device or app".
- Exiting the `claude` process takes the session offline.
- To forbid it entirely: the `disableRemoteControl` setting.

### A.5 Security notes

- The local session makes **outbound HTTPS only and opens no inbound port**, so this adds no listener on ms01.
  Traffic goes through the Anthropic API over TLS with short-lived, single-purpose credentials.
- While connected, the **transcript (messages, responses, tool activity) is stored on Anthropic servers**.
  These sessions show portfolio and broker data, so connect only the sessions you need, and disconnect when done.
- **Who can approve:** any device signed in to the operator's claude.ai account that can open the session.
  Turn on **Trusted Devices** (beta; Pro/Max: "Require trusted devices" on the Account or Cowork settings
  page): each phone or browser enrolls its own key, and a sign-in older than 18 hours needs a Face ID / Touch
  ID / passkey step-up. Sessions that were already running when you turn it on are not covered until they end.
- Remote Control does not change the session's permission mode. Sessions running in `auto` or
  `bypassPermissions` mode show fewer prompts on the phone because fewer prompts exist.

### A.6 Telegram "channels" plugin: TRIAL ONLY, on a separate bot

Channels push chat messages into a running session (research preview). The Telegram plugin needs **Bun**,
which is **not installed on ms01**.

**Finding: you cannot turn prompt relay off in the official Telegram plugin.** The plugin source
(`external_plugins/telegram/server.ts`, read 2026-10-09) declares `claude/channel/permission: {}`
unconditionally, and there is no env var or `access.json` switch to undo that. (The docs only say a *server*
opts out by omitting the key.) With relay on, **any allowlisted Telegram sender can allow or deny tool calls**
in that session. The requirement "prompt relay OFF" is therefore met another way: run the trial session in
`dontAsk` mode. The docs say that mode "auto-denies every tool call that would otherwise prompt you", so no
permission prompt exists to relay. That relay never fires in `dontAsk` mode is our inference, **NOT VERIFIED**
on device.

Trial steps (operator; nothing here is automated):

1. In BotFather, `/newbot`, and create a **new** bot used only for this trial. Do **not** reuse the CIO or
   alert bot token: a second `getUpdates` poller on the same token would steal updates from the production
   callback poller, and real approvals stay in the guard ledger flow.
2. Install Bun (operator decision; adds a runtime to the host).
3. In a scratch directory, not a repo worktree with credentials: `claude`, then
   `/plugin install telegram@claude-plugins-official` (user scope), then `/telegram:configure <token>`.
   This writes the token to `~/.claude/channels/telegram/.env`. Never paste it into a repo or a chat log.
4. Restart with relay neutralised:
   `claude --permission-mode dontAsk --channels plugin:telegram@claude-plugins-official`
5. DM the bot, get the pairing code, run `/telegram:access pair <code>`, then
   `/telegram:access policy allowlist`.
6. The reply tool itself needs approval, and `dontAsk` denies it. Allow only that tool (look up its exact name
   with `/mcp`; the name is **NOT VERIFIED**), e.g. `--allowedTools "<telegram reply tool>"`.
7. Exit criteria for the trial: no `permission_request` ever reaches Telegram; messages from a non-allowlisted
   account are silently dropped; the production Telegram bots are unaffected.
8. End: exit the session. Channels only run while a session started with `--channels` is open.

| promote rebind | `scripts/cio_phase2_exact_main_deploy.sh` default bound units (skipped while not installed) |

Lane registry: not changed. It lists scheduled lanes, and the relay, gateway and executor services are not
lanes either.

**Why a separate unit rather than a route on the n8n relay:** `scripts/n8n_run_relay.py:guard_bind` admits
only `127.0.0.1` and docker bridge gateways (`172.16-31.x.1`). That listener is the only one the n8n lab may
reach. Adding the tailnet to it would widen the n8n-facing surface and mix two authorities in one process.
The phone endpoint has its own `guard_bind`, which admits only an IPv4 in `100.64.0.0/10` that **equals
`tailscale ip -4`**. It refuses `0.0.0.0`, loopback, LAN, other tailnet IPs, privileged ports and the
gateway's `BLOCKED_PORTS`. `--host auto` resolves the IP at start, so the unit hard-codes no address. If
Tailscale is down, the endpoint refuses to start and systemd retries every 30 s.

### B.2 The endpoint

`GET /phone/status`. Every other method or path is refused (`405`/`404`). Peers outside `100.64.0.0/10` get
`403 phone_bad_peer` before auth. Response is at most 2 KB, `Cache-Control: no-store`, cached 20 s server-side:

```json
{"schema":"PhoneStatus@v1","authority":"READ_ONLY_ADVISORY","as_of":"…",
 "n8n":{"healthy":true,"age_s":291,"workflows_registered":6},
 "run_failed_24h":{"count":1,"lanes":["n8n-lab-watchdog"]},
 "incidents":{"open":115,"p1":1,"p2":26,"age_s":216},
 "guard":{"pending_requests":0},
 "release":{"served_sha":"377e9b536afc"},
 "disk":{"used_pct":82.7},
 "missing":[]}
```

Sources, all existing (CC single-source rule: nothing is fetched, nothing calls n8n, the gateway or a broker):

| field | source |
|---|---|
| `n8n.healthy`, `age_s` | `data/runtime/n8n_lab_watchdog_last.json` (`ok` and `checked_at` <= 15 min old) |
| `n8n.workflows_registered` | `config/lane_registry.json` in the served release: ACTIVE lanes with `scheduler.kind == "n8n"`. This counts the registry, not n8n's own "active" flag. n8n's API is not queried. |
| `run_failed_24h` | coordination ledger `runs` table via `project_runs(state="RUN_FAILED")` (read-only sqlite) |
| `incidents` | `data/runtime/n8n_incident_fanin_last.json` (`open`, `by_severity`) |
| `guard.pending_requests` | `~/.cursor/approvals/remote_requests.json`: a **count** of unexpired `PENDING` rows. No ids, scopes, reasons or code fingerprints leave the function. |
| `release.served_sha` | `BUILD_SHA` of the release the unit runs from (CURRENT) |
| `disk.used_pct` | `statvfs` of the state root, the same arithmetic as `df` Use% (a local syscall, not a data fetch) |

An absent or unreadable source is named in `missing` and its value is `null`. It is never guessed.

### B.3 Auth

Headers: `X-Phone-Ts` (unix seconds), `X-Phone-Nonce` (`[A-Za-z0-9_-]{8,64}`), `X-Phone-Sig` (64 hex),
`X-Phone-Alg` (`hmac-sha256` by default, or `sha256-envelope`). Canonical message:
`<ts>\n<nonce>\nGET\n/phone/status`.

- `hmac-sha256`: `HMAC-SHA256(key, message)`. Use it from a laptop, `openssl`, or a scripting app.
- `sha256-envelope`: `SHA-256(key + "\n" + message + "\n" + key)`. Use it from Apple Shortcuts (see B.4).
- Window ±60 s. Nonces are single-use and remembered for 120 s. A nonce is recorded only after the signature
  verifies, so unauthenticated traffic cannot fill the cache (cap 4096, fail-closed `429`).
- Rate limits: 20 requests/min per peer IP and 60/min overall. Failed attempts count.
- Key: `TRADEAI_PHONE_STATUS_HMAC_KEY` (>= 32 bytes) from Bitwarden SM via `render_env` -> `%t/tradeai/env`.
  `TRADEAI_PHONE_STATUS_HMAC_KEY_PREVIOUS` is accepted during rotation. A missing or short key refuses startup.
- The only thing written to disk is `data/runtime/phone_status_last.json`: last outcome plus counters, no
  headers, no key, no client data.

### B.4 Shortcuts has no HMAC: the approach and the honest trade-off

Apple Shortcuts has a native **Generate Hash** action (MD5/SHA-1/SHA-256/SHA-512) but **no HMAC** action.
Computing HMAC by hand needs byte-wise XOR with ipad/opad, which Shortcuts cannot reasonably do. The options:

| option | key on the wire | replay | key at rest | verdict |
|---|---|---|---|---|
| static bearer, rotated weekly, Tailscale ACL as the boundary | yes, every request | yes, until rotation (inside WireGuard) | in the Shortcut | works, weakest |
| **SHA-256 envelope** `H(K‖msg‖K)` with ts+nonce (built) | **no** | **no** (±60 s plus single-use nonce) | in the Shortcut | **chosen for Shortcuts** |
| true HMAC in a scripting app (e.g. Scriptable) or "Run JavaScript on Web Page" | no | no | in that app | possible; adds a third-party app or a web-page context |
| "Run Script over SSH" to compute the HMAC on ms01 | n/a | n/a | SSH key on the phone | **rejected**: puts a shell credential on the phone, far more power than a status read |

Why the envelope is acceptable here: the server re-derives the message from validated fields (ts = digits,
nonce = a fixed alphabet, the path must equal `/phone/status`). A length-extension forgery of `H(K‖msg)`
therefore cannot produce a different valid message, and the trailing `‖K` blocks the extension anyway. It is
still not HMAC, and HMAC's proofs do not apply to it. That is accepted for a read-only, tailnet-only endpoint.

**What does not change with any option:** the key sits in the Shortcut. If iCloud sync for Shortcuts is on,
the key is also in iCloud. The real boundary is therefore the **Tailscale ACL plus the phone's device lock**.
Auth on top of that limits the damage from a compromised tailnet peer or a captured request. The data is
read-only status with no codes or secrets, which is why this is acceptable. The same reasoning is why the
same key must never authorise an approval (section C).

### B.5 Shortcut recipe (operator builds it on the iPhone)

1. **Text**: paste the key (from Bitwarden; do not send it through Messages, Telegram or email). Set it as
   variable `K`.
2. **Date**: `1970-01-01T00:00:00Z`. **Get Time Between Dates**: from that date to *Current Date* in
   **Seconds**. **Round Number** to ones. Set as `TS`. (Whether Shortcuts reads the `Z` as UTC is **NOT
   VERIFIED**. If the endpoint answers `phone_stale_ts`, show `TS` and compare it with `date +%s` on ms01. An
   offset of exactly your UTC offset means the date was read as local time; add or subtract that offset.)
3. **Random Number** between 100000000 and 999999999. **Text** `ios-[Random Number]-[TS]` -> set as `N`.
4. **Text** with five line breaks, exactly:
   ```
   [K]
   [TS]
   [N]
   GET
   /phone/status
   [K]
   ```
5. **Generate Hash**: Type **SHA256**, input = the Text from step 4. Set as `SIG`.
6. **Get Contents of URL**: `http://100.66.120.124:18093/phone/status` (or
   `http://ms01-openclaw.tail163d14.ts.net:18093/phone/status` with MagicDNS). Method **GET**. Headers:
   `X-Phone-Ts` = TS, `X-Phone-Nonce` = N, `X-Phone-Alg` = `sha256-envelope`, `X-Phone-Sig` = SIG.
   (Plain `http://` is encrypted by WireGuard inside the tailnet. Whether Shortcuts allows plain-http here
   without a prompt is **NOT VERIFIED** on device. If it does not, put Tailscale Serve's tailnet-only HTTPS in
   front, under its own grant. Do **not** use Funnel.)
7. **Get Dictionary from Input**, then **Show Result**, or build a one-line text from `n8n.healthy`,
   `run_failed_24h.count`, `incidents.p1`, `guard.pending_requests`, `disk.used_pct`.
8. Optional: add it to the Home Screen or as a widget. Each run uses a fresh nonce.

   random bytes (e.g. 64 hex chars). Then `python scripts/secrets/render_env.py --now`.
2. Dry-run (no listener; prints `key_present` and the payload size, never the key):
   `~/trade-ai-v12-rebuild/trade-ai-v12-rebuild/.venv/bin/python ~/trade-ai-releases/portfolio-server/CURRENT/scripts/phone_status_endpoint.py --dry-run`
3. Tailscale ACL: allow only the operator's phone (user or tag) to `ms01-openclaw:18093`. A default
   "allow all" tailnet policy would let every node try; the HMAC still applies, but the ACL is the intended
   boundary.
4. Host firewall: if ufw filters `tailscale0`, allow exactly `in on tailscale0 to 100.66.120.124 port 18093
   proto tcp`. Do not open any other interface.
5. Install and enable the unit with the commands in the unit file header. Then
   `systemctl --user status tradeai-phone-status` and `ss -ltnp | grep 18093`. It must show
   `100.66.120.124:18093` and never `0.0.0.0` or `*`.

7. Rotation (every 30 d, or now if the phone is lost): new value in SM, then render, then restart the unit.
   The old value stays valid as `_PREVIOUS` until the next render. Update the Shortcut's Text action.

Rollback: `systemctl --user disable --now tradeai-phone-status.service`, remove the installed unit file,
delete the SM key. Nothing else depends on the endpoint.

## C. Approvals from the phone: DESIGN ONLY, not built

**Today's path, unchanged:** a guard request mints a single-use code. The operator approves from Telegram, in
an allowlisted chat. `scripts/lib/guard_remote_approval.py` (`verify_and_consume` / `settle_by_request_id`)
moves the request PENDING -> APPROVED and the grant lands in the **guard grant ledger**
(`.cursor/hooks/guard_ledger.py`). The phone already has this path, because Telegram is on the phone.

**If a phone-native approval is ever added**, it must be a different *transport* into that same flow, never a
second writer: it would call the same settle function, with the same chat or identity allowlist and the same
single-use code, and leave the same audit row. The status endpoint's key would not be accepted for it.

**Why a second approval path is rejected for now:**

1. **One writer, one audit trail.** Two paths that can mint grants means two authentication perimeters to keep
   equivalent, and two places to look when a grant appears. The ledger's provenance check
   (`unprovenanced_grants`) assumes one origin.
2. **Credential escalation.** The Shortcut key sits in plaintext in Shortcuts and possibly in iCloud. As a
   read-only key its loss leaks a status summary. As an approval key its loss would mint config-write or
   release grants. Same storage, much higher stakes.
3. **No second factor.** Telegram approval binds to an allowlisted chat plus a code shown only to the operator.
   A Shortcut tap has neither, unless rebuilt, and rebuilding it means rebuilding the Telegram flow.
4. **Never route around a denial.** A second path is exactly how a denied or expired request gets "approved
   anyway". The existing flow already handles EXPIRED, DENIED_WRONG_CHAT and FORBIDDEN_SCOPE.
5. **Remote Control is not an approval path either.** A tap there approves a Claude Code tool call, not a
   guard tier (A.3).

Revisit only if Telegram becomes unavailable as a transport, and then as a transport into the same settle
function under an AGENTS.md-reviewed change.
