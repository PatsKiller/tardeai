### The finding that matters: `cost_cap` wears two different shapes

| shape | n (all time) | what it actually is |
|---|---:|---|
| `HTTP 429 {"code": "COST_CAP_EXCEEDED"}` | 82 | the daily spend cap, honestly labelled |
| `HTTP 500 {"code": "RESERVATION_FAILED", "message": "COST_CAP_EXCEEDED: daily request cap"}` | 114 | **the same cap, wearing a server error** |

Classifying on the response *code* would file those 114 as provider errors and
send someone to debug a bridge that is behaving exactly as configured. The
classifier therefore reads the **message**, not the code, and both land in
`cost_cap` with `is_worker_bug: false`.

Together they are 196 of 302 all-time failures and 130 of the last 7 days —
**57% of the trailing window is the process cap doing its job.**

`execution_language` is the other 93: the model wrote execution verbs, the
output was correctly refused. Also not a worker bug.

**No failure class in the last 7 days is a worker bug** (`worker_bug_n = 0`).
Only 5 of 228 are retryable at all.

Exposed on the product as `research_fail_histogram`, cached on
`(path, mtime_ns, size, window, hour)` so a 9MB ledger is not re-read on every
`/v3/cio/home` — a new failure is still picked up on its next read, and the
trailing window advances hourly on a quiet ledger.

## 20 — execution-language failures are never requeued

`replay_decision` refuses the enqueue outright. The model was instructed not to
write execution verbs and did; running it again spends cap to be refused again.

One correctly-refused output blocks the plan even when a *retryable* truncation
also exists in its history — a truncation cannot launder an execution-language
refusal.

Wired into `enqueue_research_request` as an **opt-in** `list_prior_failures`
callback: existing callers are unchanged, and when the ledger read throws the
gate fails soft (an unreadable ledger must not block legitimate work). On a
block, no request row is written at all.

## 21 — truncated replay: at most 1 per plan per calendar day

Retryable, but capped. The cap is enforced by *eligibility*, not by raising
anything: `MAX_REPLAYS_PER_PLAN_PER_DAY = 1`, and `raises_cost_cap` is `false`
on every decision. A plan whose only history is `cost_cap` waits for the cap
window rather than retrying into a closed door.

| prior history | allow | reason |
|---|---|---|
| none | ✅ | `no_prior_failure` |
| `execution_language` (any) | ❌ | `execution_language_non_retryable` |
| all `cost_cap` | ❌ | `cost_cap_wait_for_window` |
| `truncated` today | ❌ | `truncated_replay_cap_reached` |
| `truncated` 3d ago | ✅ | `retryable_within_cap` |
