### Trap 1 — `--t2` maps to `BB.text3`, NOT `BB.text2`

`BB.text2` is `#cbd5e1`, which the mockup does not use at all. A name-based mapping
(`t2 → text2`) is wrong by one shade. **This is precisely the class of error that broke the
previous round** — that one named `--at-*` Active Trader tokens against the v3 slate family. The
mapping must be made by VALUE, never by name.

### Trap 2 — `--purple #a855f7` is explicitly deprecated by the page's own design system

`watchTokens.ts` carries a deprecation map whose first line is:

```
#a855f7 (purple accents) → T.extIntel.hermes (muted, badges only) or BB.text2
```

`T.extIntel.hermes` is `#a78bfa` — a *different* value. So the mockup specifies a hue the page has
formally retired. It is marked "reserved, unused in v1" and appears nowhere in the rendered
markup, so **it has no effect on v1**. Recommendation: do not define it. If v2 needs a purple, use
`T.extIntel.hermes`.

### The 4 real gaps

`--bg2`, `--sunk`, `--line2`, `--t3` have no equivalent anywhere in `BB`, `T`, or `RAIL`. They are
in the contract's manifest, so adding them is not a manifest violation — but they are new tokens in
the design system and `check_design_tokens.sh` runs inside `npm run build` with **defense at a
0-violation baseline**. They must be added to `watchTokens.ts` as named exports, never as raw hex
in components, or the build will block.

### One semantic inversion worth flagging

The mockup uses `#0a0e1a` (`BB.bgPanel`) as the **page** background and `#111827` (`BB.bgShift`) as
the **panel** surface. Today `/v3/defense` uses `BB.bg` (`#0f172a`) as the page ground, and
`#0f172a` appears nowhere in the mockup. So this is not merely a token match — it is a deliberate
re-grounding of the page one step darker. Correct per the contract (structure and style frozen),
but it changes every surface, not just new sections.

### Not sourceable — the "Read" column (section 4)

The mockup shows interpretive one-liners:

> *"Already your largest — confirmation, not an entry"*
> *"Narrow participation — one third above 20DMA"*
> *"Strongest slope on the board (+6.1)"*

None of these strings exists anywhere in the tree. What `transitions_today` actually carries is a
restatement of the data:

```json
{"sector":"Financials","etf":"XLF","from":"WEAKENING","to":"LEADING","severity":"urgent",
 "line":"⚠ Financials: WEAKENING→LEADING (day 2 confirm) · RS +2.4% (5d) · breadth 59% …"}
```

That is the *input* to a read, not the read. The Read column is **authored judgement**. It is
either a new deterministic generator (a small rules table: largest-exposure → "confirmation not an
entry"; breadth < 40% → "narrow participation"; max slope → "strongest slope") or it renders `unk`.
**Needs a decision.** Inventing prose per row without a rule is exactly the fabrication the
contract forbids.

### Partly sourceable — Sector rank in Your book (section 7)

Sampled the 8 largest positions ≥$10K:

```
SCHD  $209K  sector=Dividend Equity        rank=None
JEPI  $ 84K  sector=Income / Covered Call  rank=None
V     $ 74K  sector=Financial Services     rank=None   <- alias failure, fixable
DIVI  $ 43K  sector=None                   rank=None
XLI   $ 36K  sector=Industrials            rank=7      <- only one that resolved
ARKX  $ 30K  sector=None                   rank=None
BND   $ 27K  sector=Fixed Income           rank=None
```

Two separate causes, one fixable and one not:

1. **Alias failure — fixable.** `symbol_profiles.sector` uses Finviz names; `list_sectors()` uses
   ETF labels. Applying `_sector_aliases` in reverse resolves them:
   `Financial Services → Financials #2` · `Consumer Cyclical → Consumer Discretionary #9` ·
   `Basic Materials → Materials #4`. This makes V render `#2 Financials`, matching the mockup.
   Same root cause as the SL-S1 join bug; the reverse map is one function.
2. **Funds have no GICS sector — not fixable by aliasing.** The mockup already anticipates this and
   renders `broad` for SCHD/JEPI and `thematic` for ARKX. **But there is no source for that
   classification.** `config/fund_lookthrough.json` carries `name`, `source`, `weights`,
   `lookthrough`, `industries` — nothing that says broad vs thematic. It is *derivable* from weight
   count (SCHD 10 sectors, JEPI 11, ARKX 5, XLI 1) but that is inventing a policy. Per the contract
   these render `unk` with a reason unless the operator supplies the classification. **Needs a
   decision** — the mockup shows them as confident dim labels, not `unk`.

### Ambiguous — industry `rank` inside the Sector Leaders card

The mockup shows `Oil & Gas Integrated · rank 8`, `Oil & Gas Equipment & Services · rank 3`,

## S0.5 — THE DISPERSION BUG DOES NOT EXIST

Contract §6 states production renders `buy names` for Oil & Gas Integrated at spread 38.1pp,
top-quartile excess −9.14pp, n=14.

Live production, right now:

```
Oil & Gas Integrated            n=14  spread=13.14  excess=+8.67  -> 'buy names'
Oil & Gas Equipment & Services  n=14  spread=38.10  excess=-9.14  -> 'mixed'
Thermal Coal                    n=3   spread=None   excess=None   -> None
```

**The numbers cited belong to Oil & Gas Equipment & Services, not Oil & Gas Integrated.** Both have
n=14, which is how they came to be transposed. And the industry that actually carries
spread 38.1 / excess −9.14 already returns **`mixed`**, not `buy names`.

The logic, quoted in full:

```python
if spread >= DISPERSION_NAMES_SPREAD_PP and excess is not None and excess >= DISPERSION_NAMES_EXCESS_PP:
    return "buy names"
if spread <= DISPERSION_ETF_SPREAD_PP:
    return "buy the ETF"
return "mixed"
```

Spread and excess are **not** read independently — `buy names` requires BOTH `spread >= 12` AND
`excess >= 4`. A negative excess can never satisfy `>= 4`, so **negative excess already vetoes
"buy names" at any spread.** The requested fix is already the behaviour, and a test already asserts
it (`test_wide_spread_alone_does_not_buy_names_without_etf_excess`, added at `da237c2b`: spread
40.0 with excess 1.0 must return `mixed`).

Oil & Gas Integrated is genuinely `buy names`: its top quartile beats XLE by 8.67pp.

### But there IS a real spec item hiding inside it

The mockup renders **two different strings** for what the code calls one verdict:

- Oil & Gas Integrated → amber chip `wide spread, leaders still trail XLE`
- Oil & Gas Equipment & Services → neutral chip `mixed`

So the mockup asks for a **fourth verdict state**: when excess is negative, say so explicitly
instead of hiding it behind the generic `mixed`. That is a legitimate and useful requirement — it
makes the negative-excess case legible, which is what §6 was really reaching for. It is a
presentation addition, not a threshold change, and it is **in the mockup**, so it is in scope.

Recommended: keep thresholds at 12/4/6, keep the logic, add a `mixed_leaders_trail` variant when
`excess < 0`, with a test. Chip text is a VALUE per §1 and comes from the API either way.
