## Community versus paid requirements

It excludes projects, workflow/credential sharing, SSO, environments, native Git, external secrets, external binary storage, external log streaming and multi-main. Registration unlocks folders, editor debugging and custom execution data without a paid plan. Exact commercial tier allocations can change; the comparison itself points to pricing as the final commercial matrix, which was outside this docs.n8n.io-only review.

## Isolation and authority restrictions

Official [isolation guidance](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/isolate-n8n.md) disables diagnostics/update/template calls to n8n servers. **Those flags do not prove a firewall or arbitrary internet/host-route denial.** Official [SSRF guidance](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/enable-ssrf-protection.md) explicitly makes infrastructure network controls primary and application SSRF protection additional defense; it describes HTTP allow/block lists, redirects and DNS validation. A broad relay-host allowlist must not become permission to every host port.

TradeAI's stricter SOURCE_ONLY design remains: loopback UI; only the scoped relay host route/port, plus n8n's own required internal PostgreSQL connection; deny TradeAI API/DOF/DB/broker/model/notification routes and internet egress unless a separate exact requirement is approved. Only relay bearer belongs in n8n; HMAC/model/broker keys stay on the host. Docker/firewall/IPv6/DNS reachability must be observed independently; earlier TCP probes are incomplete rule proof. Nothing in these official docs ratifies AGENTS3.0.0 or permits a provider/Agent/sender authority change.

Official [node controls](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/nodes.md) support explicit `NODES_EXCLUDE` and community-package disabling; [security variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/security.md) support `N8N_BLOCK_ENV_ACCESS_IN_NODE`. Retain explicit command/SSH/email/file exclusions and no unapproved community nodes. Check exact installed node variants and workflow/code parameters: excluding some nodes does not prove Code/HTTP/network confinement. Official [runner hardening](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/harden-task-runners.md) recommends external runner isolation, unprivileged users, read-only roots and sensitive-/proc restrictions; actual runner mode/isolation remains independently measurable, not inferred from availability.

If unused, official docs recommend disabling the public API with `N8N_PUBLIC_API_DISABLED`; zero API keys is not proof that the API is disabled. Propose a separate approved configuration action, never change it silently. [Public API guidance](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/disable-the-public-api.md)

## Retention: defaults versus measured policy

Official [execution variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions.md) document defaults: successall/errorall, progressfalse, manualtrue, pruneenabled, age336h, maximum10000 and hard-delete buffer1h. The measured168h and successnone are intentional overrides, not defaults. Keep them; verify workflow-level settings, error payload redaction and actual effective configuration before acceptance.

**Correction to an overly broad40 claim:** configured168h does not guarantee every stored error/payload disappears within seven days. Official [pruning semantics](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/manage-execution-data.md) exclude new/running/waiting and annotated executions, use soft then hard deletion and a safety buffer, and prune by age or count. Existing stale DB running labels therefore warrant bounded investigation, not an assumed prune guarantee or automatic deletion. Successful n8n coordination metadata is not the durable host RunReceipt/output/consumer chain.

## Database and independent recovery

Official [database support](https://docs.n8n.io/deploy/host-n8n/configure-n8n/choose-n8ns-database.md) currently names PostgreSQL17/18 as supported and16 as compatibility support, with latest minor recommended. Thus the observed16.15 supports a **separate17-or18 migration plan**, not a claim that PostgreSQL16 is wholly unsupported or an immediate mixed scheduler/DB migration. Choose target at the approved migration decision after current support/recovery review.

The same official page requires table-schema create/modify capability and demonstrates a dedicated database user with database-scoped grants, rather than cluster superuser. **Inference/recommendation:** remove unnecessary superuser/create-role/create-DB/replication/bypass-RLS authority from the n8n application role while preserving ownership/schema-migration permissions, connection and recovery. The13:15 role metadata still has all five flags; permission design, backup/restore verification and exact operator-approved migration remain outstanding. Do not treat official sample SQL as a complete drop-in migration for the existing schema.

Official [backup/restore guidance](https://docs.n8n.io/deploy/host-n8n/keep-n8n-running/backup-and-restore.md) requires the user folder/config/encryption key plus external DB and any applicable external/custom-node data. CLI workflow/credential exports omit users/roles, execution history/logs, settings and key; exports alone are not full recovery. The encryption key is required to decrypt restored credentials. Protect recoverable key custody separately; do not print keys or create decrypted exports. [Encryption key guidance](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/set-a-custom-encryption-key.md)

Nightly DB backups and weekly isolated restore drills are **TradeAI program proposals**, not a frequency mandated by official docs. Preserve independent host backup/watchdog/recovery scheduling.
