Why `30 3 * * 0` and a flag: a five-field cron cannot say "first Sunday". `30 3 1-7 * 0` ORs
day-of-month with day-of-week, so it fires on days 1–7 and on every Sunday. The live workflow fires
every Sunday and the script is a no-op unless the date is day 1–7. The shadow (dry-run) prints the
plan every Sunday.

All thresholds are in `config/ops_lanes.json` (`OpsLanesConfig@v1`); paths there start with `~`
and expand to the running user's home, so the same code runs from a release and the dev tree.

## Thresholds and findings

Findings use the incident fan-in shape (`source, item, severity, detail, artifact_rel, store,
detected_at`) under `fanin_findings`, with `fanin_wired: false`. No lane sends anything.

- **storage-watch:** for each configured filesystem, WARN (P2) at ≥ 80% used and CRIT (P1) at
  ≥ 90%. Inodes use the same thresholds. The Postgres log dir at ≥ 2 GiB is P3. Leftover
  `m2_shadow_test_*` DBs ≥ 25 is P3. Worktrees ≥ 200 is P3. A heavy root growing ≥ 2 GiB/day since
  the last receipt is P3. `du` runs on a fixed list of roots (`heavy_roots`), one at a time, under
  `ionice -c3 nice -n 19 du -x -s` with a 180 s timeout per root. It never scans the whole tree.
  The trade_ai size and top 10 relations come from catalog queries on a read-only session. The M2
  count is one catalog SELECT through `docker exec`.
- **backup-verify:** the trade_ai dump must be < 26 h old (P1 if not). Its size must be within
  ±30% of the median of the last 7 days (P2). The history comes from `backup.log` and earlier
  receipts. The dump must read end to end with ≥ 600 tables (P1 if not). The n8n lab dump must
  have a receipt with `ok`, be < 26 h old, still be on disk at its recorded size, and pass
  `pg_restore --list` with table-data entries ≥ the live count it recorded (P1 if any fails). The
  three weekly Drive family stamps must be ≤ 8 days old (P2 if stale, P1 if missing). A missing or
  failed dump is P1.
- **restore drill:** a refusal is P2, or P1 when no dump exists. A restore with a non-zero exit or
  a timeout is P1. ERROR lines are P2. Any top-20 table outside max(1000 rows, 15%) is P1. A
  throwaway DB left behind is P1.

### Deviation from the brief: `pg_restore --list` on the trade_ai dump

`linux_launchers/run_pg_backup.sh` writes `--format=plain | gzip -9` (`.sql.gz`). `pg_restore`
cannot read plain SQL. For `.sql.gz` the lane streams the whole file through `pigz -dc`. That
checks the gzip CRC, counts `CREATE TABLE` and `COPY` statements, and requires pg_dump's closing
`-- PostgreSQL database dump complete` line. A custom-format `.dump`, if one appears, gets
`pg_restore --list`. Live measurement 2026-10-09: 699 `CREATE TABLE`, 682 `COPY`, trailer
present, 2 m 34 s on a loaded host.

### Fix: `scripts/backup_verify.py:31`

The old lookup was `<code root>/backups/db`, which never existed. So the monthly step reported
FAIL from both the release and the dev tree. The dump dir now comes from config: `~/db_backups`,
overridable with `TRADEAI_DB_BACKUP_DIR`. The no-flag form is still the
platform-maintenance-monthly step, with its report and alert. The new `--dry-run` / `--write`
modes never send.

## Restore drill: what it may write

It writes only a database it created itself, named `restore_drill_<YYYYMMDD>`.
Guarded since `n8nmat/restore-drill-guard` (2026-10-09; audit F D4/D5); receipt `TradeAiRestoreDrill@v2`.

1. The name must fullmatch `^restore_drill_\d{8}$` (ASCII digits), or the drill refuses.
2. Disk floor: estimate = live `pg_database_size` minus the excluded-data schemas
   (`intelligence`, `memory_r10_m2`). The drill refuses unless the free space on the cluster's
   filesystem is > 2 × estimate × 1.15.
3. Role guard. The drill connects as a dedicated role from `TRADEAI_RESTORE_DRILL_DB_USER` /
   `_PASSWORD` (environment, or the operator-only 0600 file `~/.config/tradeai/restore_drill_db.env`).
   There is no fallback to the live `DB_USER`. It refuses unless the role has CREATEDB; is not a
   superuser and has no CREATEROLE, REPLICATION or BYPASSRLS; is not the live user; and is not a
   member of the live database's owner. It also refuses unless the template `restore_drill_template`
   exists, unless psql supports `\restrict`, and if the name already exists. A leftover database is
   reported, never dropped.
4. Dump guard pre-scan (`scripts/lib/restore_dump_guard.py`). The drill reads the whole SQL stream
   before it creates anything. A `.sql.gz` is decompressed. A `.dump` is rendered with
   `pg_restore --no-owner --no-acl -f -`, which writes to stdout and never to a database. The drill
   refuses with a P1 if it finds any of these:
   - any psql meta-command, at the start of a line or mid-line, other than pg_dump's own
     `\restrict` / `\unrestrict`
   - `CREATE`, `DROP` or `ALTER DATABASE`
   - `ALTER SYSTEM`
   - role DDL, `SET`/`RESET ROLE`, `SESSION AUTHORIZATION` or `set_config('role')`
   - `GRANT` / `REVOKE`
   - `COPY … PROGRAM`, or any `COPY` that is not `FROM stdin`
   - a dump that ends inside a COPY block

   COPY data rows are only counted. A match inside a function body is refused too.
5. `CREATE DATABASE … TEMPLATE restore_drill_template`, then
   `COMMENT ON DATABASE … 'tradeai-restore-drill run <run_id>'`, then restore:
   producer | guard | `psql -X -d <throwaway>`. psql's first input line is
   `\restrict <random per-run key>`, so psql refuses every backslash command for the whole session.
   The guard runs again on this stream. On a violation it kills psql before it sends the line, and
   kills psql rather than closing its stdin, so a partial statement never runs. The restore is niced
   and has a 4 h timeout. ERROR lines that match `tolerated_error_regexes` (only
   `must be owner of extension X`: the template owns the extensions) are counted separately.
6. Exact `count(*)` of the 20 largest live tables plus the `key_tables`
   (`config/ops_lanes.json`). Each count must EQUAL the number of rows in that table's COPY block in
   the dump. A table with no COPY block falls back to the live `reltuples` estimate ±15% (min 1000).
   The drift from the live estimate is recorded either way.
7. `DROP DATABASE`, attempted after every create, even when a step failed. It runs only if the
   name matches the regex, equals the name this run created, and the COMMENT carries this run's id.

`--dry-run` prints the plan only and reads only the catalog. `--dry-run --scan-dump` adds the
pre-scan, which reads the whole dump file. On the 2026-10-09 dump it took 83 s, covered 18.2 M
lines and 682 COPY blocks, and found no violation.

## Stage plan

1. **Shadow.** The operator imports the `-shadow` workflow (inactive) and activates it, each under
   a grant whose reason names the workflow id (the #1554 P16 check: a grant naming only the lane
   is `NAME_ONLY_GRANT`). The workflow fires `mode=dry_run` through the relay. The executor writes
   a `RunReceipt@v1`.
2. **Canary.** Import and activate the live workflow under a grant naming its id. One fire in
   `live` writes the lane receipt. For the restore drill, the canary is one manual
   natural-equivalent fire on a first Sunday, after the CREATEDB role exists.
3. **Cutover.** These lanes have no cron line, so nothing is retired. The registry row flips to
   `scheduler.kind = n8n` with `expression` = the live workflow id and `match` = the script path,
   `state ACTIVE`, under a `config-write` grant.

## Rollback

- Shadow or canary: deactivate the workflow (`active false`). Nothing else changed, because there
  is no cron line or unit to restore. Leave the registry row `NEVER_SCHEDULED`.
- After cutover: deactivate the workflow and flip the row back to `kind none` /
  `NEVER_SCHEDULED` under the same grant tier. These lanes had no previous scheduler, so there is
  no line to re-enable.
- Code: revert this PR. `backup_verify.py`'s no-flag path stays compatible with the monthly step
  either way.
- Restore drill failure: if the receipt shows `throwaway:left_behind`, the operator drops
  `restore_drill_<date>` by hand after checking its COMMENT marker. The lane never retries a drop
  on a name it did not create.
